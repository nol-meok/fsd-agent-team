features사용자 동작 / 유즈케이스 / 비즈니스 로직
▶

역할

  • 사용자가 "하는 것"을 담당: ~하기 (로그인하기, 검색하기, 리뷰쓰기)
  • 비즈니스 로직, 상태 관리, API 호출, 인터랙션 UI 포함
  • 하나의 feature = 하나의 유즈케이스

여기에 넣는 것

ui/인터랙션 포함 UI (LoginForm, SearchBar)
model/상태관리 훅, 비즈니스 로직, 타입
api/해당 feature의 API 호출
// features/write-review/ui/WriteReviewForm.tsx
export const WriteReviewForm = () => {
  const { mutate, isPending } = useWriteReview();
  const handleSubmit = (data: ReviewFormData) => {
    mutate(data); // ← 사용자 액션 + 비즈니스 로직
  };
  return <form onSubmit={handleSubmit}>...</form>;
};

// features/write-review/model/useWriteReview.ts
export const useWriteReview = () => {
  return useMutation({
    mutationFn: writeReviewApi,
    onSuccess: () => { ... },
  });
};
// feature에서 다른 feature import
import { useAuth } from '@/features/auth'; // ← feature끼리 의존 금지
// 해결: entities를 통해 데이터 공유

entities도메인 데이터 모델 - "타입 + API만, UI 없음"
▶

역할

서비스가 다루는 데이터의 구조(타입)와 데이터 접근(API)만 정의한다. UI는 만들지 않는다.

여기에 넣는 것

model/types.ts데이터 구조 타입 정의 (필수)
api/데이터 CRUD API 호출 (선택)
model/ 유틸데이터 변환, 매핑 함수 (선택)

여기에 넣지 않는 것

ui/ 폴더UI 컴포넌트는 widgets 또는 features에서 만든다
인터랙션 로직features에서 처리
*.module.scssUI가 없으므로 스타일도 없음
// entities/restaurant/model/types.ts
export interface Restaurant {
  id: string;
  name: string;
  address: string;
  rating: number;
  category: string;
}

// entities/restaurant/api/restaurantApi.ts
export const getRestaurant = async (id: string): Promise<Restaurant> => {
  const res = await fetch(`/api/restaurants/${id}`);
  const data = await res.json();
  return mapToRestaurant(data);
};

// entities/restaurant/index.ts
export type { Restaurant } from './model/types';
export { getRestaurant, getRestaurantList } from './api/restaurantApi';
// entities에 UI 컴포넌트 넣기 = 금지
entities/restaurant/
├── ui/                     ← ui 폴더 자체가 없어야 함
│   └── RestaurantCard.tsx  ← widgets에서 만들어야 함
├── model/types.ts
└── index.ts

구조 (ui/ 없음)

entity-name/
├── model/
│   └── types.ts       # 필수! 데이터 타입
├── api/
│   └── entityApi.ts   # 선택. CRUD API
└── index.ts           # public API

예시

entities/

├── restaurant/    # { id, name, address, rating }
├── review/        # { id, content, score, authorId }

Slice 내부 구조

widgets, features, entities의 각 슬라이스는 동일한 내부 구조를 따릅니다.

slice-name/
├── ui/                    # 컴포넌트
│   ├── ComponentA.tsx
│   ├── ComponentB.tsx
│   └── ComponentA.module.scss
├── model/                 # 상태, 로직, 타입
│   ├── types.ts           # 타입 정의 (entities 필수)
│   ├── useSlice.ts        # 커스텀 훅
│   └── store.ts           # zustand store 등
├── api/                   # API 호출
│   └── sliceApi.ts
└── index.ts               # public API (필수!)

index.ts (Public API)

외부에서 슬라이스에 접근할 때 반드시 index.ts를 통해서만 접근합니다.

// entities/restaurant/index.ts
export { RestaurantCard } from './ui/RestaurantCard';
export { getRestaurant, getRestaurantList } from './api/restaurantApi';
export type { Restaurant } from './model/types';

// 사용 시
import { RestaurantCard, type Restaurant } from '@/entities/restaurant';

import { RestaurantCard } from '@/entities/restaurant/ui/RestaurantCard';
import type { Restaurant } from '@/entities/restaurant/model/types';

Anti-Patterns

자주 발생하는 FSD 위반 패턴과 올바른 해결 방법입니다.

1. app에 스타일/로직 넣기

src/app/
├── page.tsx
├── Page.module.scss    ← 스타일 파일 금지!
└── utils.ts            ← 로직 파일 금지!
src/app/page.tsx          ← 위젯 조합만
src/widgets/home-hero/
└── ui/
    ├── HomeHero.tsx
    └── HomeHero.module.scss  ← 스타일은 여기

2. feature끼리 의존

// features/search/model/useSearch.ts
import { useAuth } from '@/features/auth'; // ← 금지!
// entities/user/model/types.ts에 공유 타입 정의
// features/auth → entities/user 사용
// features/search → entities/user 사용 (독립적으로)

3. entities에 UI 컴포넌트 넣기

// entities는 데이터만! UI 넣지 않는다
entities/restaurant/
├── ui/                     ← 이 폴더 자체가 없어야 함
│   └── RestaurantCard.tsx
├── model/types.ts
└── index.ts
// entities는 타입 + API만
entities/restaurant/
├── model/types.ts     # Restaurant 타입 정의
├── api/restaurantApi.ts
└── index.ts

// UI는 widgets에서 만든다
widgets/restaurant-list/
└── ui/RestaurantCard.tsx  # entities의 타입을 import해서 사용

4. shared에 도메인 코드

shared/ui/RestaurantCard.tsx   ← 도메인 종속! entities로
shared/lib/useAuth.ts          ← 인증 도메인! features로

5. 슬라이스 내부 직접 import

import { Button } from '@/shared/ui/Button/Button'; // 내부 경로 직접 접근
import { Button } from '@/shared/ui'; // index.ts를 통해 접근

6. widget끼리 import

// widgets/review-feed/ui/ReviewFeed.tsx
import { Header } from '@/widgets/header'; // ← 같은 레이어 import 금지!
// app/page.tsx에서 각각 독립적으로 조합
import { Header } from '@/widgets/header';
import { ReviewFeed } from '@/widgets/review-feed';

7. function 키워드 사용

export function RestaurantCard() { ... }
function handleClick() { ... }
export const RestaurantCard = () => { ... };
const handleClick = () => { ... };

배치 가이드 (어디에 넣어야 하지?)

Q1. 다른 프로젝트에 그대로 가져가도 동작하는가?
→ Yes → shared (Button, useDebounce, formatDate)
→ No → Q2로
Q2. DB에 저장되는 데이터 구조 / 단순 표시 UI인가?
→ Yes → entities (User 타입, RestaurantCard)
→ No → Q3로
Q3. 사용자 액션을 처리하는가? (클릭, 입력, 제출, 검색)
→ Yes → features (LoginForm, useSearch, writeReviewApi)
→ No → Q4로
Q4. 페이지의 한 영역 / 독립 UI 블록인가?
→ Yes → widgets (Header, HomeHero, Sidebar, Dukbae)
→ No → Q5로
Q5. 라우팅/페이지 정의인가?
→ Yes → app (page.tsx, layout.tsx만)

실전 워크플로우

"리뷰 작성 기능"을 만드는 전체 과정을 예시로 보여줍니다.

Step 1. /plan 리뷰 작성 기능

Planner 출력 예시

## 작업 계획: 리뷰 작성 기능

### 영향 범위
| 코드 | 레이어 | 이유 |
|------|--------|------|
| Review 타입 | entities/review | 데이터 모델 |
| ReviewItem UI | entities/review | 표시 전용 |
| reviewApi | entities/review | CRUD API |
| WriteReviewForm | features/write-review | 사용자 액션 |
| useWriteReview | features/write-review | 비즈니스 로직 |
| ReviewFeed widget | widgets/review-feed | 섹션 조합 |
| 리뷰 페이지 | app/reviews | 라우팅 |

### 작업 순서
1. entities/review (타입 → UI → API)
2. features/write-review (훅 → 폼 UI)
3. widgets/review-feed (조합)
4. app/reviews/page.tsx (배치)
